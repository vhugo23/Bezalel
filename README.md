# PrepCrew

A voice interview coach for hardware and embedded engineering students.

Built for CodeRED: Orion at the University of Houston.

Live site: _(fill in after deploy)_

## What it does

1. You paste a hardware job posting and your resume.
2. A voice interviewer opens on one of your resume projects and follows up on what you say.
3. Circuit walkthrough: you get a schematic with a planted fault. You talk through your debugging and click nodes to probe voltages. The interviewer reacts to your probes.
4. Draw it first: you draw a schematic from a prompt and explain it!
5. When the session ends, evaluators grade every answer in parallel and quote the evidence. The debugging process is graded too: did you check the supply first, verify ground, isolate the fault before swapping parts, and state a hypothesis.
6. Each flagged gap links to a skill node and a short lesson. You retest, and the mastery chart updates.
7. Your next session starts from your weak spots from the last one!

## How it differs from existing tools

Generic interview tools such as Big Interview score delivery. Voltage Learning offers a hardware question bank. Job search copilots such as Jobright exist. In our research we did not find a tool that grades a debugging process or connects an interview gap to a lesson and a retest. That is the part we built.

## A note on the 3D breadboard

Real hardware interviews commonly ask candidates to draw and explain circuits and to talk through debugging. We found no evidence that interviews use a bench or a 3D simulator. Any breadboard view in PrepCrew is our own teaching aid and is not meant to match a real interview.

## How it works

```
Browser (laptop)   mic audio over websocket, schematic view, dashboard (SSE for live agent status)
Browser (iPad)     Pencil canvas, paired to the laptop session by code
FastAPI + asyncio  on Vultr, Docker Compose, reverse proxy with TLS
```

| Component | Job | Tool |
|---|---|---|
| Voice loop | Speech to text, interviewer turns, streamed speech, barge in | Gemini Flash, ElevenLabs |
| Session manager | State machine: intake, interview, walkthrough, drill, debrief, lesson, retest | Python |
| Circuit | DC nodal solver, one netlist per scenario, probe events | Python |
| Evaluators | One call per answer per rubric, run in parallel, schema checked, quotes verified against the answer | Gemini (`EVALUATOR_MODEL`) |
| Curriculum | Skill graph, lessons, mastery updates | Python |
| Memory | Weak spots and goals carried into the next session | Backboard |
| Data | `answer_scores` and `probe_events` hypertables, daily mastery continuous aggregate | Tiger Data |
| Whiteboard | Pencil canvas, vision critique of a stroke snapshot plus the spoken explanation | Gemini |

The live loop uses Flash because turn latency decides whether the conversation feels natural. Grading runs in the background and can use a stronger, slower Gemini model (`EVALUATOR_MODEL`), because quality matters more than speed there.

Short notes for each component are in `docs/architecture/`.

## Run it locally

You need Python 3.11 or newer and Docker.

```
cp .env.example .env     # then fill in your own keys
docker compose up --build
```

Keys needed in `.env`:

| Variable | Used for |
|---|---|
| `GEMINI_API_KEY` | Interviewer, grading and whiteboard vision |
| `ELEVENLABS_API_KEY` | Streamed speech |
| `BACKBOARD_API_KEY` | Memory |
| `DATABASE_URL` | Tiger Data connection string (any Postgres works) |

Never commit `.env`.

## API

| Route | Purpose |
|---|---|
| `POST /sessions` | Start a session |
| `WS /ws/voice/{session_id}` | Mic audio in, speech out |
| `WS /ws/board/{session_id}` | Schematic probes and iPad canvas |
| `POST /sessions/{id}/end` | End the session and run the evaluators |
| `GET /sessions/{id}/events` | Live agent status over SSE |
| `GET /skills` | Skill graph |
| `POST /lessons/{skill_id}` | Open a lesson |

Final request and response shapes will live in `contracts/`.

## Known limits

- Freehand schematic reading by the model is best effort. The snap-in schematic builder gives an exact netlist, and grading uses that when it is available.
- The circuit solver covers DC analysis only, for a small set of authored scenarios.
- No code sandbox.
